# v1.8.4 brief

**Requested:** No new request — this is a same-session fix for a regression `v1.8.3`'s own deploy step caused.

**What happened:** Deploying `v1.8.3` printed a warning from Wrangler: *"Because 'workers_dev' is not in your Wrangler file, it will be enabled for this deployment by default."* Checked directly rather than dismissing the warning as noise — `curl` against `www.visithra-agro.workers.dev` returned `200`, confirming the route the user had deliberately disabled via the Cloudflare dashboard (once the custom domain went live) had come back.

**Root cause:** `workers_dev` wasn't set in `wrangler.jsonc` at all, so it fell back to Wrangler's default (`true`) on every deploy. Disabling the route from the dashboard is a one-time, deploy-time state — it isn't something Wrangler remembers or preserves across a subsequent `wrangler deploy`, which re-applies whatever the config file says (or defaults to) every time.

**Fix:**
- Added `"workers_dev": false` to `wrangler.jsonc`, so the setting is version-controlled and survives every future deploy rather than living only in a dashboard toggle.
- Added a `deploy.sh` pre-flight check confirming `workers_dev: false` is present before deploying.
- Added a `deploy.sh` post-deploy check confirming `www.visithra-agro.workers.dev` actually returns a non-200 response — catches this specific regression automatically instead of relying on someone reading Wrangler's console output.

**Verified:** redeployed; `workers.dev` now returns non-200; re-ran the full `DEPLOYMENT.md` §5 checklist against both `visithra-agro.in` and `www.visithra-agro.in` and confirmed both still serve correctly with matching headers and version.

**Released as:** v1.8.4 (patch — infrastructure fix, no change to site content or behavior, per `VERSIONING.md`).
