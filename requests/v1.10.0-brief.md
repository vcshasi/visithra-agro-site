# v1.10.0 brief

**Requested:**
1. "Email address : info@visithra-agro.in" (user had already created the Zoho mailbox — see the two prior chat turns confirming Zoho Mail free-plan eligibility for US/IN/EU data centres)
2. "Align the mobile numbers to have same margin"
3. "Have India and Europe Flag correspondingly somewhere for easy user identification" — later corrected mid-turn: "Instead of Europe as header for second phonenumber, change it to Germany itself" + "Also include Germany flag to it"
4. "Also include Nuremberg, Germany as second option" (address)

**Delivered:**

1. **Email:** `CONFIG.businessEmail` → `info@visithra-agro.in`. Before shipping, checked (not assumed) that DNS routing actually points at Zoho: `nslookup -type=MX visithra-agro.in` returned `mx.zoho.eu` / `mx2.zoho.eu` / `mx3.zoho.eu`, and the SPF TXT record (`v=spf1 include:zohomail.eu ~all`) and Zoho's domain-verification TXT were both present in Cloudflare DNS. That confirms mail *routing* is configured; it doesn't prove the `info@` mailbox itself is receiving mail — that can only be confirmed by the account holder sending a real test message, which is worth doing before relying on it for real enquiries. Notable: the account landed on Zoho's **EU** data centre, not IN as I'd suggested earlier in chat — not a problem (EU is also free-plan eligible), just a different data-residency outcome than the one I'd recommended.

2. **Phone number alignment:** root cause was that the region badges ("India" vs the second number's region label) are different widths, and the previous flex-row layout meant each number's start position depended on its own row's badge width — nothing actually shared a column. Fixed by converting `.phone-list`/`.addr-list` to CSS grid with `.phone-row`/`.addr-row` set to `display: contents`, which promotes each row's cells into the shared grid so the badge column is sized to the *longest* label across every row. Verified via `getBoundingClientRect()`, not by eye — both numbers now report an identical `left` value.

3. **Flags:** hand-drawn inline SVG (India: white/saffron/green tricolor + simplified chakra; Germany: black/red/gold tricolor), circular via CSS `overflow:hidden` cropping a 3:2-viewBox flag rather than an SVG `clipPath`+`id` (avoids ID-collision risk if a region is ever duplicated). **Correction mid-implementation:** the second number was originally labelled "Europe" with an EU flag (12-star ring, computed via trigonometry rather than hand-typed coordinates, to avoid a transcription error); the user then asked for the label itself to change to "Germany," so the EU flag was swapped for a German one to match — simpler flag, EU star-ring code removed as dead code rather than left unused.

4. **Second address:** `CONFIG.address` (string) → `CONFIG.addresses` (list) — India (Coimbatore, unchanged) plus a new Germany entry (Nuremberg). Rendered with the same region-badge treatment as phone numbers, reusing the same grid-alignment mechanism, without flags (only asked for on phone numbers; a plain "India"/"Germany" text label reads clearly enough on its own for a two-entry address list).

**Verified:** local preview, DOM/computed-style inspection (screenshots unreliable this session — the Browser pane wasn't focused, a known limitation, not a code issue) — correct flag SVG structure (rect/circle counts and fill colors) for both flags, identical alignment for both phone numbers and both addresses, no console errors, no horizontal overflow at desktop, 375px, or 320px viewport widths, `deploy.sh --check-only` passes.

**Released as:** v1.10.0 (minor — new Contact-section content and a real feature addition [flags, second address], consistent with v1.9.0's precedent, per `VERSIONING.md`).
