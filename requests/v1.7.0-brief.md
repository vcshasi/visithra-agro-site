# v1.7.0 brief

**Requested:** "Now I want to host this webpage in some free tier host servers" — listing performance, availability, project compatibility, easy multi-version deployment, primarily-Europe-and-India-but-worldwide audience, webpage security, and server-side security as requirements, asking for a comparison to choose from. Followed by: "Proceed with Cloudflare Pages. walk me through step by step to deploy this website with a free domain (for now)."

**Comparison presented** (Cloudflare Pages vs. Netlify, Vercel, GitHub Pages, Firebase Hosting):

| | Cloudflare Pages | Netlify | Vercel | GitHub Pages | Firebase Hosting |
|---|---|---|---|---|---|
| Europe coverage | Excellent | Strong | Strong | Good | Strong |
| India coverage | Best of the group | Good | Good, improving | Weaker | Strong |
| Free bandwidth | Unlimited | 100GB/mo | 100GB/mo | ~100GB/mo | ~11GB/mo |
| Versioned deploys/rollback | Preview URL per commit, one-click rollback | Same | Same | No native preview/rollback | Preview channels, more CLI-centric |
| Free-tier security | Built-in DDoS protection + WAF | HTTPS + headers only | Same as Netlify | Same as Netlify | HTTPS + headers only |

Recommended Cloudflare Pages given the stated Europe/India-primary audience and security priority; user chose it.

**Delivered** (repo prep — the account-creation and dashboard-connection steps are the user's own next actions, since those can't be done on their behalf):
1. Added `.gitignore`, excluding `.claude/` — discovered to be a leftover git worktree from the earlier peer-review-agent session (v1.3.1/v1.3.2 tag-collision episode), never meant to be part of the deployed site — plus standard OS junk files.
2. Added `_headers` (the file Cloudflare Pages reads automatically to apply response headers at its edge): a strict Content-Security-Policy with no `unsafe-inline` and no wildcard origins, built by directly auditing the site's actual resource usage — confirmed via `grep` across `index.html`/`script.js` that the only external origins are Google Fonts (`fonts.googleapis.com`/`fonts.gstatic.com`) and the Web3Forms API (`api.web3forms.com`), and that there are no inline `<script>` blocks, no inline `style=""` attributes, and no `eval`-like patterns — so the strict policy (no `'unsafe-inline'` needed anywhere) is safe. Also added `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` disabling unused browser features, and `Strict-Transport-Security` (HSTS).
3. Rewrote `README.md`'s hosting section with the actual Cloudflare Pages deployment steps (GitHub connection, build settings for a no-build static site, the preview-deploy/one-click-rollback workflow), replacing the earlier "here are your options" text now that a host is decided.

**Verified:** rather than trust the CSP would work once deployed, temporarily mirrored the same headers on the local test server (`serve.ps1`), reloaded the site fresh, and confirmed: Google Fonts still resolve correctly (the `<h1>`'s computed `font-family` reads `"Playfair Display", Georgia, serif` — the actual web font, not a fallback), and a real, live, end-to-end contact-form submission through the Web3Forms API still succeeds with the strict CSP active (`connect-src`/`form-action` correctly permit the cross-origin POST) — confirmed via the "Thank you — your enquiry has been sent" success status. No console errors, no CSP violation reports, on a completely fresh browser tab (to rule out any stale/cached state from earlier testing in this session).
