# v1.8.3 brief

**Requested:** "Help me buy and setup domain name for the deployed website" (`.in`, cost-efficient) → registrar comparison → "Go with Namecheap, walk me through it" → user independently bought `visithra-agro.in` at **GoDaddy** instead → "Host the webpage in visithra-agro.in domain" → walked through connecting it to the existing Cloudflare-hosted site → "Yes, go ahead and ship v1.8.3".

**Delivered:** `visithra-agro.in` (and `www.visithra-agro.in`) is now the site's live domain, replacing `*.workers.dev`.

**What actually happened, in order:**
1. Registrar comparison done for Namecheap/GoDaddy/Porkbun/BigRock; recommended Namecheap. User bought `visithra-agro.in` at GoDaddy instead — their call, no issue, walkthrough adapted to GoDaddy.
2. Added the domain to Cloudflare, got its nameservers, pointed GoDaddy's nameserver settings at them.
3. **Incident 1:** entering the nameservers at GoDaddy failed with a generic error — root cause was a typo (`cloudfare.com` for `cloudflare.com`) caught by reading GoDaddy's per-field message rather than the generic banner.
4. Attempted to attach `visithra-agro.in` as a Cloudflare Custom Domain on the existing `www` Worker — failed: "Hostname already has externally managed DNS records."
5. **Incident 2:** the freshly-purchased domain had GoDaddy-auto-provisioned "Website Builder" placeholder content wired to the apex via leftover DNS records, imported into the Cloudflare zone when it was first added. Diagnosed via a screenshot of the DNS Records list; deleted the stale `A`/`CNAME`/`_domainconnect` records; the Custom Domain attach then succeeded for both apex and `www`.
6. First verification pass caught a **second layer** of the same problem: `visithra-agro.in` returned `200`, from a genuine Cloudflare IP address, but with GoDaddy's own CSP header and GoDaddy Website Builder's placeholder HTML in the body — not this site. Root cause: GoDaddy's Website Builder product is itself fronted by Cloudflare (a different zone), so IP address and status code alone didn't distinguish "our Worker" from "GoDaddy's product also on Cloudflare." Re-verified with the actual response body and header contents after the user fixed it on their end; confirmed clean on a second, independent check.
7. User deliberately disabled the old `www.visithra-agro.workers.dev` Worker route — no longer needed once the custom domain works.
8. Shipped this release: version bump, `README.md`'s live URL and hosting section updated, `deploy.sh`'s `SITE_URL` repointed at the custom domain (was still checking the now-disabled `workers.dev` URL, which would have made every future `--verify-only`/deploy run fail) plus a new independent check for the `www` alias, `DEPLOYMENT.md` §8 added documenting the connection procedure and both incidents so they aren't repeated, `SECURITY.md` updated (HSTS preload no longer blocked but deliberately not auto-submitted; Web3Forms domain-restriction confirmed Pro-only, not free-tier).

**Verified (live, not dashboard status):** on both `visithra-agro.in` and `www.visithra-agro.in` — response body contains this site's real content, CSP/HSTS/X-Frame-Options headers match `_headers` exactly, `/styles.css` and `/script.js` return 200, `.git/config`/`README.md`/`deploy.sh` return 404, live version meta tag (`1.8.2` at time of check, before this release's own bump) matched the working directory. `workers.dev` confirmed genuinely disabled (404, not a transient blip — retried 3×) per the user's explicit choice, not treated as a bug.

**Not done, and deliberately not done automatically:** HSTS preload submission at hstspreload.org — newly unblocked by having a real custom domain, but preload-list inclusion is effectively permanent, so it needs the user's own deliberate go-ahead, not a default action bundled into a routine version release.

**Released as:** v1.8.3 (patch — infrastructure/hosting change, no change to site behavior or content, per `VERSIONING.md`).
