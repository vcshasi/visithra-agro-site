# v1.6.6 brief

**Requested:** "http://localhost:8811/index.html#products lands perfectly in the product section. But clicking on a product in under product in header section doesnot. Fix this."

**Delivered:**
Reproduced the difference between the two paths: a plain `#products` URL is a single, native browser anchor jump — nothing to race. The header submenu's click handler, on the other hand, issued two separate smooth-scroll calls back to back: `document.getElementById('products').scrollIntoView({block: 'start'})` for the vertical scroll, and `card.scrollIntoView({block: 'nearest', inline: 'start'})` to bring the chosen family's card into view horizontally within `.product-track`. `scrollIntoView`'s ancestor-walk isn't limited to the nearest scrollable ancestor — it can also move the page's own vertical scroll if it judges the target isn't sufficiently "in view" vertically from wherever the page happens to be at that instant — so both calls ended up trying to drive the same vertical scroll position simultaneously, landing somewhere neither call intended.

Confirmed this diagnosis directly: with both scrolls forced to apply instantly (removing the animation-timing race), the landing position was correct; the bug only showed up under real smooth-scroll timing.

Fixed by adding `scrollTrackToCard(card)`, which computes the needed horizontal offset and applies it via `track.scrollTo({left: ...})` directly — never touching `document`/`window` scroll at all — mirroring the technique `scrollGalleryToSlide()` already used for the inner photo galleries (its own comment already explained exactly this class of bug for that case; the outer family track just hadn't been given the same treatment). Applied it at all three places that scroll the family track: the header submenu handler, the carousel prev/next buttons, and autoplay's family-to-family transition — the latter two weren't visibly broken (nothing else competes with them for the vertical scroll), but carried the same latent risk and are now equally safe.

**Verified:** confirmed `scrollTrackToCard` never changes `window.scrollY` when called in isolation, so the two calls in the submenu handler are now structurally unable to race regardless of real-world animation timing. Re-confirmed the family-switcher wraparound (added in v1.6.1) still works correctly after the refactor. No console errors.

**Released as:** v1.6.6 (patch — a bug fix to existing navigation behavior, per `VERSIONING.md`).
